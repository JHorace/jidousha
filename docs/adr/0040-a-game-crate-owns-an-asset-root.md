# ADR-0040: A game crate owns an asset root, and `dist/<name>/` is repository-shaped

Status: accepted · 2026-08-23

## Context

ADR-0038 put prototypes in this workspace at `games/<name>/` so that living here
is what makes one built, linted, verified and published. giri, the first of
them, arrived with art: four portraits, four dungeon icons, five stat icons,
generated by a script committed beside them. That art is giri's, so it belongs
at `games/giri/assets/`.

It could not load from there. `asset_source(root)` fetches relative to the page
on the web, and `tools/build-web` staged exactly one directory beside a page —
the repository root's `assets/`. A game that owned its art therefore had three
options, and all three were bad:

- put it in the repository's shared root, where it no longer travels with the
  game and where two prototypes' `icon_coin.png` collide;
- give up the asset source and compile the bytes in;
- give up the web build.

giri took the second: `include_bytes!` and a `MemorySource`, thirteen entries and
a `to_vec()` each. It works, and the game recorded it as a workaround rather
than a choice (`games/giri/FINDINGS.md` G-005). The general form of the finding
is one sentence: **a game crate cannot have an asset root.**

The four `docs/api/` documents also do not say any of this. `asset_source`'s
entry is four lines and an example with `"assets"` in it, and nothing in the
surface says what that root means on the web — that it meant "one fixed
directory per repository" was a fact about the build tool, which is exactly why a
game author could not find it.

## Decision

**A game crate gets a real asset root: `games/<name>/assets/`, loaded through
`asset_source` on native and on the web alike.** (Owner's decision, 2026-08-23.)

The mechanism is one rule about the build:

> **CONTRACT: `dist/<name>/` is repository-shaped.** `tools/build-web` stages
> every asset root a page's code can name *under the page, at the path the code
> names it by*. A root string is therefore a path from the workspace root:
> `"assets"` for the repository's shared root, `"games/giri/assets"` for a
> game's own. The native loader resolves that string against the workspace root
> and the web loader fetches it relative to the page, and because the directory
> sits at the same relative path in both, the same string means the same
> pictures. That is assets.md §2's identical-paths CONTRACT, kept rather than
> excepted.

Two roots reach a page, and which ones is not a guess:

- the repository's shared `assets/`, which the engine's examples load from,
  staged for every page — unchanged from what they had before;
- the game's own `<crate>/assets/`, staged for that game's page only.

`tools/check-assets` enforces the rule from the other side: a file under
`games/<name>/` must load from `games/<name>/assets`, and everything else from
`assets`. Those are the two directories the build stages, so a root outside the
rule is art that reads on a developer's disk and 404s on the deployed page —
which is precisely the class of asset bug that only appears after shipping, and
the one this repository has spent the most words on (assets.md §2).

## Rationale

**Why not bless `include_bytes!` as the answer** — which was G-005's other
stated option, and is declined:

- It does not scale past a handful of files. The owner's curated pixel-art
  library is incoming; fifty roles would be fifty `include_bytes!` and a binary
  carrying all of it, on the platform where module size is most expensive.
- It turns every art tweak into a recompile. Changing a picture should be
  changing a file.
- Art that cannot travel with its game contradicts what ADR-0038 put games in
  this repository to get. A prototype whose pictures are welded into its
  executable is a prototype that cannot hand its art to anything — not the web
  build, not a repository of its own when it leaves, not the check that reads
  the files.

**Why the mirrored path rather than staging a game's art as `assets/` beside its
page.** `dist/giri/assets/` reads better as a URL, and it cannot work: it would
make `"assets"` mean the repository's root directory in an example and the
game's own directory in a game, from an identical string, decided by something
neither the loader nor the reader can see. The alternatives were each worse than
the redundancy in `/giri/games/giri/assets/icon_coin.png`:

- resolving the root against the calling crate's manifest directory would break
  every example, whose art is at the repository root and stays there;
- baking `CARGO_MANIFEST_DIR` into the string at compile time gives an absolute
  path from the build machine, and a different string per platform — which is
  the `cfg` `asset_source` exists to keep out of games;
- a second, game-only way to name a root is a second way to do something that
  already has one (conventions §1).

One string, one directory, one rule that a reader can check by looking at the
repository: the URL is the price and it is small.

**What this costs a game that leaves.** ADR-0038 says a prototype that ships
under its own name gets a repository of its own. There, the game *is* the
repository, its art is at `assets/`, and its root string becomes `"assets"` —
one line, changed on the day the crate moves, by the same person doing the move.
The rule does not change: the root is still the path from the repository root to
the directory, and `tools/build-web` still stages it under the page.

**Native resolution is the process's working directory**, which is the workspace
root for every tool here (`tools/verify`, `tools/test`, and `cargo run -p giri`
run from it). That is unchanged by this decision and is now written down in
assets.md §2 rather than implied. A shipped native binary run from elsewhere
would not find its art; nothing distributes one today, and the day something
does, the fix is a decision about installation layout rather than about this
seam.

## Consequences

- `tools/build-web <game>` stages the game's own asset directory; `--all` does
  it for every game, so the deploy workflow needs no change — it uploads `dist/`
  verbatim and always did.
- `tools/serve-web` serves what `build-web` staged, so the local page and the
  deployed page carry the same directories.
- `tools/check-assets` gained one rule and checks a game's paths for the first
  time: giri's thirteen were invisible to it while they were compiled in.
- giri's `include_bytes!` table is gone, and `games/giri/assets/` is now a
  directory a person can drop a picture into.
- The four `docs/api/` documents say what a root means on the web, at
  `asset_source`, which is where G-005 says a game author looks for it.
